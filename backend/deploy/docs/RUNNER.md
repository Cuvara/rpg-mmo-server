# Dev runner and backup rehearsal

This runbook covers the self-hosted `dev` jobs in `.github/workflows/cd.yml` and the guarded backup-only rehearsal in `.github/workflows/backup-dev.yml`. The latter is a manual, backup-only path: it never deploys. Both use GitHub Environment `dev` and the `[self-hosted, dev]` runner labels. The repository's `dev` environment has not been verified to have protection rules or a deployment branch policy; configure and verify those settings before registering a runner. A repository runner inventory showed zero registered runners during the P3A investigation, so neither workflow can complete until an authorized operator provisions a suitable runner. This document does not authorize registering one.

## Runner trust boundary

The current dev environment uses `DEPLOY_MODE=k8s` and the `k3d-rpg-dev` cluster. The runner needs a Bash/Linux runtime, GitHub Actions runner tooling, `kubectl` and the dev context, PostgreSQL/Redis backup utilities in the target pods, and (for optional Redis scratch restore) Docker CLI access to a daemon. Normal CD deployment also needs the dev control plane and Docker/k3d access. Docker socket and kubeconfig access grant substantial control over the runner host and dev cluster; treat that host as trusted infrastructure.

For the interim single-PC option, use a dedicated WSL distro and a dedicated unprivileged Linux user solely for the runner. Do not use Docker Desktop; connect only to the existing native WSL daemon. Keep the distro, home directory, kubeconfig and runner state separate from other work, and provision only dev access. Do not copy production or staging credentials into the distro. Repo-scoped one-job JIT runners reduce persistent registration but do not sandbox workflow code from Docker or Kubernetes access.

The stronger long-term alternative is a separate, patched, dedicated host with an isolated service account, encrypted storage, restricted firewall, repo-only ephemeral runners, and a limited route to the dev cluster and backup destination. The current k3d API and durable backup path are local to the dev host, so a separate host requires a designed private connectivity path; do not expose PostgreSQL or Redis publicly.

## Secrets and runner lifecycle

- Before any runner is registered, a repository admin must configure the `dev` GitHub Environment with required reviewers and a deployment branch policy that permits only `develop` (and any other explicitly protected deployment branches). Verify the live configuration with `gh api repos/Cuvara/rpg-mmo-server/environments/dev`; confirm `protection_rules` includes required reviewers and `deployment_branch_policy` is restricted to the intended branches. These settings are not assumed to exist, and this runbook does not change them.
- The backup job itself runs only for `github.ref == 'refs/heads/develop'` and its first step checks the dispatch actor through the GitHub API, allowing only `write` or `admin` permission. Keep `develop` protected and limit write access to trusted maintainers. The workflow references no other secrets, but passes `REDIS_PASSWORD` only to the backup step that may need it; the in-file guard does not replace environment reviewers or the deployment branch policy.
- The backup rehearsal uses the runner's dev kubeconfig and does not need PostgreSQL passwords passed as workflow secrets. It passes `REDIS_PASSWORD` only to the backup step in case Redis AUTH is configured. Environment secrets remain a risk if the workflow is changed; the ref and actor checks do not replace the required reviewer and branch policy gates. Do not add database dumps, kubeconfig, JIT configuration, runner tokens, or secret values to Git, Actions artifacts, logs, chat, or reports.
- For normal CD on this workstation, provision two independent repo-scoped JIT configurations, each ephemeral and limited to one job, with unique names and labels `[self-hosted, dev]`. CD has two dev-labelled self-hosted jobs: `db-migrate` (“Back up databases”) followed by `deploy`. One single-job runner cannot serve both; have two online for the run. Treat each encoded JIT configuration as a secret, pass it directly to runner configuration through a protected transient input, and never print or persist it. The JIT API procedure does not require creating a PAT or a runner registration token.
- Do not start runner instances until an approved maintenance window. Verify their names, labels and online state without displaying configuration. Start the intended workflow, watch its exact jobs and target environment, and keep both instances available until their corresponding jobs finish.
- After the run, verify the JIT instances are offline/removed, remove temporary runner and kubeconfig state, and confirm no runner process remains. Do not alter or restart the host's native Docker service or unrelated stacks.

## Soak exclusion

Do not run a dev backup, restore rehearsal, or deployment during a testlab soak. Reserve a no-soak interval that covers the full backup/restore or CD job and cleanup. Do not start a soak until the jobs finish and all ephemeral runner processes are gone. The backup workflow checks the runner's process table for a testlab S09/soak process and fails when it finds one.

The testlab currently has no shared lock-file convention, and process visibility can differ between a runner and the testlab host. The preflight is a secondary guard, not a reservation system: the operator must confirm the lab slot is idle before dispatch and keep it idle for the run. Propose that the factory testlab acquire and release `.testlab-runs/LAB-SLOT.lock` for every run/suite/sweep/soak operation, with the backup and CD preflight checking that same host-visible lock before starting. This task does not change the factory.

## Backup-only rehearsal

Use `.github/workflows/backup-dev.yml` from `develop`, manually, in a reserved no-soak and no-CD window. The job is restricted to `refs/heads/develop` and actors with write or admin permission. It runs on `[self-hosted, dev]` in Environment `dev`. Its concurrency group is `backup-dev` with `cancel-in-progress: false`, separate from CD's `cd-dev` group: backup runs cannot cancel or be cancelled by CD, and vice versa. This does not serialize backup against deployment, so operators must schedule a no-CD window; within the backup group, a newer queued backup may replace an older pending backup while an active run is allowed to finish. It calls `backup.sh` and `redis-backup.sh` without `--skip-missing`; a missing target must fail. It requires exactly two newly created PostgreSQL `.dump` files and one Redis `.rdb` file. Its only uploaded artifact is a TSV containing relative file names, byte sizes, and SHA-256 checksums; it never uploads dump contents. The files remain in the configured restricted `BACKUP_DIR`, which must be provisioned with sufficient free space and durable, access-controlled storage.

By default the workflow only takes and inventories backups. If `restore_scratch` is selected, it additionally invokes `restore.sh --target <unique-run-specific-database> --yes` for each fresh PostgreSQL archive and `redis-restore.sh --mode scratch` for the fresh RDB. PostgreSQL scratch databases are created in the dev data cluster and remain there after the job; record their names from the run logs and arrange their removal through the database operator after reviewing the restore evidence. Redis restore uses a disposable scratch container/volume and cleans them up automatically. Neither restore command targets a live database or Redis dataset.

## Verification and evidence

For a backup-only run, confirm the Actions run used the intended commit and configured `dev` environment protections; the correct dev context and namespace; both PostgreSQL dump files and the Redis RDB; successful script archive checks; and a metadata artifact listing only names, sizes and checksums. Confirm the files landed under the intended restricted backup path and note its retention/durability. If scratch restore was requested, confirm PostgreSQL restore completion to the unique scratch names and Redis scratch load success, then schedule removal of the PostgreSQL scratch databases. Record the run URL/ID, commit SHA, UTC timestamps, runner names, job results, metadata, restore targets, warnings and teardown state. Do not attach raw archives.

For a normal CD run, confirm the “Back up databases” job reached the in-cluster Postgres and Redis targets before reviewing the subsequent deploy and smoke jobs. Do not dispatch CD just to rehearse a backup: it proceeds to deployment. A missing-target skip, incomplete metadata, unexpected target, soak overlap, failed restore, or runner left online makes the evidence failed or inconclusive; stop and investigate before any deployment follow-up.

The existing hosted `restore-drill.yml` exercises synthetic data in disposable services. It is useful for the isolated restore workflow but is not evidence that dev cluster backups work.
