## Implementation constraint: prefer existing Nakama capabilities

User direction, 2026-09-07: prefer Nakama's built-in capabilities before adding custom infrastructure. This applies to every stage below.

- Keep Nakama as the owner of account authentication, session refresh, wallet/ledger, leaderboard and meta storage. Use its SDK and runtime APIs; custom RPCs should be thin authorization and game-rule adapters.
- For reward deduplication, first validate Nakama Storage Engine conditional writes together with `nk.MultiUpdate` to commit the receipt and wallet update atomically. Verify support and conflict/rollback behavior against the pinned Nakama version before implementation. Ledger metadata alone is not an idempotency guarantee.
- Prefer server-only Nakama storage permissions and authoritative leaderboard configuration. Do not create a second wallet, account service or direct-SQL replacement for Nakama-owned data.
- Social, groups, chat and matchmaking should evaluate Nakama's existing APIs when those features enter scope; this audit does not add gameplay features.
- Keep the existing custom realtime simulation, prediction and map handoff scope. Assess any proposed custom mechanism against what Nakama already provides, and document the remaining gap first. This preference does not by itself authorize replacing the game server with Nakama matches.
- Reliable delivery from the game server may still need a small persistent pending record: an atomic grant inside Nakama cannot recover a reward that was never delivered. Choose the smallest mechanism needed after validating the built-in grant path.

Reference: [Nakama best practices](https://heroiclabs.com/docs/nakama/server-framework/introduction/best-practices/) describes conditional storage writes and atomic storage/wallet updates through MultiUpdate.

## Priority findings

### F01 - P0: economy RPC callers are not restricted to servers

Evidence: `backend/nakama/main.go:41-48` registers reward_kill, reward_kills and submit_kill directly. `backend/nakama/economy/reward_batch.go:75-102` accepts user_id and kills from the request and calls WalletUpdate without checking caller context. The legacy reward and submit handlers have the same missing boundary.

Nakama RPC supports authenticated client calls as well as runtime HTTP key calls. A comment saying a handler is internal does not enforce that restriction. A normal account can therefore reach this mutation path when the registered RPC endpoint is exposed in the ordinary way. No attack was executed against a running service.

Fix: share a server-only caller guard across all mutation RPCs; reject user-session invocations before parsing/granting, enforce the intended server credential path, and preserve public read APIs. Test anonymous, valid client-session, invalid server credential and valid server calls. Include tests asserting no wallet or leaderboard call occurred after rejection.

Reference: [Nakama runtime introduction](https://heroiclabs.com/docs/nakama/server-framework/introduction/) documents distinguishing client/server calls by user ID in context; [server-to-server RPC](https://heroiclabs.com/docs/nakama/server-framework/runtime-examples/server-to-server/) documents runtime HTTP key use.

### F02 - P1: kill leaderboard is created with client writes enabled

Evidence: `backend/nakama/economy/leaderboard.go:24-29` passes `false` for authoritative. This exposes a second score mutation path independently of F01.

Fix: make the leaderboard authoritative and explicitly migrate/replace any existing board with the old setting. Do not assume calling the idempotent creation method changes an existing board. Verify ordinary client record writes fail and server increments succeed.

### F03 - P1: game-server pre-join connections have no deadline or admission bound

Evidence: `GameServer/Server/GameServer.cs:785-827` starts a task for every accepted socket and awaits the first frame. `GameServer/Net/Connection.cs:450-455` creates its own cancellation source, with no handshake timeout. Heartbeat tasks only start after a successful join. The capacity check at GameServer.cs:863 counts authenticated connections only. The finalizer disposes `conn`, which is still null on early handshake failures, so malformed-frame exceptions also lack guaranteed transport cleanup.

Trigger: peers connect and send no complete join frame. They can retain sockets/tasks outside the player cap. Server cancellation is not linked to that first read.

Fix: a bounded pending-handshake pool, absolute handshake deadline, cancellation linked to host shutdown, and guaranteed ownership/disposal of accepted transports on every exit. Apply source-IP controls with allowance for shared NATs. Validate idle, partial-prefix, partial-body, malformed and canceled handshakes. Measure active pending handshakes and rejects separately from online players.

### F04 - P1: authenticated input and transfer work is unbounded

Evidence: GameServer.cs:1024-1043 accepts every decoded input and starts every transfer request as an independent task. `GameServer/World/EcsWorld.cs:1291-1302` appends to `_pendingInputs` without a bound. Tick processing coalesces movement later, after decoding, allocation and queue growth have already happened.

Fix: per-connection message/byte budgets, bounded input ingestion, and exactly one transfer operation per connection. Coalesce movement before queue growth, but preserve distinct attack/edge-triggered actions. Reserve separate control-message capacity and record drops/rate limits. Test flooding alongside legitimate players; legitimate tick/ack latency and memory must remain bounded.

### F05 - P1: map transfer is incomplete across client, server and persistence

Evidence: `netcode/Runtime/Client/NetworkClient.cs:309-320` calls Leave then ConnectAsync, without sending TransferMap or awaiting TransferMapResp. `GameSessionClient.cs:206-213` only handles snapshots. Meanwhile GameServer.cs:1100 ignores the boolean returned by AsyncSaver.SavePlayerAsync and returns `Ok = true` even if saving failed.

The client takes the ordinary disconnect/hold path instead of the backend's save-and-remove path. This creates an old-map ownership window while the new map can load or save the same user. The current database upsert has no owner/version predicate (`GameServer/Persistence/PostgresPlayerStore.cs:34-43`), so an old server or old periodic snapshot can overwrite a newer state. Exact timing needs a multi-server regression test; the missing protocol and ignored save result are direct code findings.

Fix: implement a complete transfer state machine: freeze/quiesce old input, save a final state, fail closed if save fails, acknowledge transfer and hand off ownership with an epoch/fencing token before destination admission. Serialize same-user persistence or reject stale versions in storage, including periodic saves already in flight. Protect against duplicate transfer requests. Changing the client alone does not solve stale writers.

Acceptance: transfer under delayed/failed DB writes and concurrent periodic saves never returns success without a committed handoff, never leaves two active owners, and never restores stale HP/map/position on relogin.

### F06 - P1: reward retry semantics can duplicate or lose currency

Evidence: `GameServer/Nakama/NakamaClient.cs:108-137` maps HttpRequestException and every non-success status to NotGranted; timeouts map to Unknown. `KillRewardBatcher.cs:107-124` requeues NotGranted, generates a fresh GUID on each send, and drops Unknown. `backend/nakama/economy/reward_batch.go:94-102` stores batch_id only in metadata, with no deduplication.

A connection failure can happen after the remote commit, not only before sending. Retrying with a new ID can double-grant; dropping an unknown result can lose a reward that never committed. Leaderboard failures after a wallet grant are also returned as success with an error field that the caller does not inspect.

Fix: stable batch IDs across retries, with a Nakama Storage Engine receipt and wallet update committed through `nk.MultiUpdate` as the first implementation candidate. Validate conditional-write conflicts roll back the wallet grant on the pinned version. Keep wallet/ledger and receipts inside Nakama's supported APIs. Add only the minimal durable sender-side pending record needed to survive a game-server restart before delivery. Reconcile leaderboard updates separately; do not assume they participate in MultiUpdate. Do not add a dedupe marker in a separate transaction and assume it closes the crash window.

Acceptance: faults before grant, after grant/before response, process restart and replay of the same batch produce exactly one wallet grant and eventual score convergence.

### F07 - P1: accumulated kill rewards can become permanently unsendable

Evidence: KillRewardBatcher flushes a killer's entire pending count; reward_batch.go:29,89 rejects counts above 1000. A NotGranted result restores the same count. There is no splitting operation.

Trigger: enough kills accumulate during an outage. Once the count exceeds 1000, every retry is rejected and put back, even after Nakama recovers.

Fix: split into accepted batch sizes with stable identity and durable remainder handling. Test counts 1000, 1001 and multiple batches, including new kills arriving during a flush. Pending state is per historical killer during an outage, not necessarily bounded by the current online-player count as the comment suggests.

### F08 - P1: automatic reconnect does not cover ordinary mobile disconnections

Evidence: NetworkClient.cs:388-404 only starts automatic reconnect when reason equals ServerShutdown. PeerClosed, HeartbeatTimeout and TransportError end the session without recovery. Gateway closure only raises an event at :459-465; NetworkBootstrap's handlers log the closure.

Fix: an explicit recovery policy by disconnect cause, with retry/backoff/jitter, a total time budget, refreshed credentials and resume handling. Never reconnect after user logout, duplicate-login kick or permanent auth failure. Recover gateway/session ownership coherently. Tie concurrent connect/reconnect/transfer work to one operation generation.

Acceptance: Wi-Fi interruption, network switch, gateway restart and app suspend/resume recover appropriately; a user cancel never leaves an old async completion connected in the background.

### F09 - P1: cancellation and failure cleanup do not cover the whole client login

Evidence: `Assets/Scripts/Nakama/NakamaSessionService.cs:82-88,214-242` checks cancellation before HTTP calls, but does not recheck after their completion before ApplySession. `NakamaAuthProvider.cs:75-83` similarly does not propagate cancellation into the RPC. NetworkClient.cs:196-197 authenticates outside the join try/catch; its generic join catch at :245-248 does not reset state or tear down the gateway. Public ConnectAsync also has no single-operation guard.

Fix: end-to-end cancellation/time budgets and a generation guard before state changes. When the SDK cannot cancel an in-flight call, discard stale completions. Use try/finally ownership of both connections and canonical state transitions for auth failure, dial failure, timeout and cancel.

Acceptance: cancel during each async phase, issue a new login, and assert no obsolete session is applied, no leaked gateway remains, and state matches actual connectivity.

### F10 - P2: persistence cadence and shutdown cost grow with player count

Evidence: AsyncSaver.cs:75-79 waits 30 seconds and then awaits a sequential save sweep; :118-127 captures all players and writes one at a time with CancellationToken.None. PostgresPlayerStore limits each command to five seconds, but there is no aggregate sweep deadline.

The effective interval includes the previous sweep duration. With N slow writes, a sweep can cost roughly N times the per-write latency; the documented 30-second window is not a strict upper bound. Background execution avoids blocking the tick, but does not guarantee timely durability or shutdown.

Fix after F05: batch writes or limited concurrency, dirty-state tracking, per-user ordering/version checks, an aggregate deadline and explicit retry ownership. Measure oldest unsaved-state age, save throughput, pool wait and drain duration. Do not merely parallelize all writes.

### F11 - P2: UI Addressables ownership is incomplete

Evidence: `Assets/Scripts/UI/AddressableAssetLoader.cs:17-24` loads a handle and discards it without Release on success/failure. `uitoolkit/Runtime/Core/IVisualTreeAssetLoader.cs:26-30` exposes no release lifetime. `UIToolkitViewFactory.cs:46,60-69` clears object references only and allows concurrent cache misses to perform duplicate loads.

Impact: repeated load/cache-clear or factory-lifetime cycles can retain Addressables references. This is a source-level ownership defect, not a measured memory-growth figure. DI/live screen usage should be checked when implementing the fix.

Fix: choose an explicit scope-owned cache/lease contract, deduplicate in-flight loads, release successful and failed handles correctly, and only unload after views stop using assets. Test repeated screen creation/disposal and concurrent requests for the same key with Addressables reference counts.

### F12 - P2 / platform gate: realtime WebGL transport is absent

Evidence: `netcode/Runtime/Transport/DefaultTransportFactory.cs:20-31` supports only TCP and KCP. TcpTransport.cs:27 explicitly documents the WebGL limitation. The project still advertises/builds WebGL.

Fix if WebGL is a release target: implement a browser-compatible transport and matching backend endpoint/advertised address for both gateway and game-session connections. Verify framing, message limits, auth, disconnect and TLS termination. A successful WebGL build is not proof of a playable connection.

### F13 - P2: production transport and HA need explicit completion gates

TCP uses NetworkStream directly, without client TLS wrapping. KCP accepts a shared transport key; that is not a demonstrated per-user authenticated key exchange. The inspected dev manifests use TCP. This does not prove any deployed production edge is unencrypted: verify the actual public route before launch and require an authenticated encrypted path for bearer tokens.

`backend/deploy/k8s/app/40-gateway.yaml:9-13,23` deliberately keeps one gateway replica because allocation single-flight is local to an instance. Increasing replicas alone risks duplicate map allocation. Keep this as a known availability limitation until distributed allocation ownership, cleanup and reconnect are tested. One live map server per map is also a gameplay/sharding contract, not something an autoscaler alone changes.

## Performance work requiring measurements

### Backend

- Preserve the dedicated tick thread and snapshot gather/encode split. Connection.GatherSnapshotView coalesces before encoding, so old criticism that dropped deltas always corrupt state is not applicable to this version.
- AOI still scans entities per viewer. Benchmark dense and sparse populations separately. The repository records a rejected spatial-grid implementation; do not reintroduce it without demonstrating improvement in the current workload.
- The fleet manifests inspected cap game-server CPU at 1000m. Compare tick duration, achieved tick rate, CPU throttling, actual frames written, coalesced snapshots and client arrivals together. A fast tick with delayed socket writers still produces poor gameplay.
- Gateway has connection/message limiters and an auth read deadline. Its blocking send queue and writes lack a separate write deadline; test slow consumers so the heartbeat path cannot become the only cleanup mechanism while itself blocked on Send.
- Make capacity admission atomic: GameServer.cs checks Count before an awaited player load and later Add. Concurrent joins can all observe the last free slot. Separate pending reservations from joined players and account for reconnect replacement semantics.

### Netcode

- TcpTransport.cs:132 allocates a body per received frame; SnapshotResolver.cs:59 allocates a resolved entity list. Measure bytes per snapshot and GC per second on the target player before introducing pooled ownership across async/event boundaries.
- WireConnection.cs:183-193 drops the oldest outbound frame regardless of message class. Control traffic should not share the movement discard policy. Leave at :219-226 enqueues Disconnect then immediately cancels/closes; it is best effort, not a flush guarantee.
- WireConnection.cs:491 uses UTC for RTT and heartbeat age. Use a monotonic clock for elapsed time, retaining UTC only for protocol fields that need it. Exercise clock jumps in tests.

### Cuvara DOTS

- EntityViewTransformSyncSystem.cs:63-72 schedules a gather job, completes it immediately and applies every hybrid Transform serially. ViewOverlaySystem.cs:55-60 adds another immediate completion. Profile both synchronization wait and managed Transform work at realistic visible counts; consider culling/LOD, lower-frequency overlays and batched presentation where measurements justify them.
- DotsEntityView.cs:74,253 queues commands without a bound, and NetworkViewCommandSystem.cs:118 drains everything in one frame. This is a package-level risk for burst producers, not proof of a backlog in the current WorldViewBinder, which polls merged world state. Instrument PendingCommands first. Any bounded/coalesced design must preserve spawn/despawn order and sufficient interpolation history.
- NetworkViewCommandSystem applies structural changes individually. Profile join/AOI-entry bursts separately from steady movement before choosing archetype batching or entity-command buffers.

### Cuvara UIToolkit

- List/grid adapters already use ListView virtualization and presenter lifecycles. Retain those benefits.
- SetItems copies the collection and rebuilds the list (`UIToolkitListAdapter.cs:173-185`, GridAdapter.cs:183-194). Appropriate for replacement, expensive for frequent small updates. Add granular refresh only for actual callers that need it; test selection/scroll position and presenter reuse.
- View creation uses reflection. Verify all runtime-created view/presenter types under Android IL2CPP and stripping; a desktop Mono pass does not establish AOT coverage. Do not label reflection itself a confirmed failure without that test.
- The HUD bridge already has change filtering and host-side write deduplication. No basis was found to recommend rewriting it as a performance fix.

## Proposed implementation sequence

Effort is an initial engineering estimate, excluding hardware procurement, deployment access and unexpected protocol migration work. Re-estimate after the first regression tests. Keep changes in separate reviewable PRs.

## Validation plan

1. Restore the repository's pinned toolchain/dependencies and run Go unit/race/vet suites, C# tests and tagged integration tests. Report skips explicitly. Run Unity package EditMode/PlayMode tests against the actual resolved package combination.
2. Add focused regression tests for F01-F09 before implementation. Include same-user concurrent operations, stale persistence writes, server crash and unknown reward outcomes.
3. Run three distinct Unity identities through login, mutual visibility, input/ack, map transfer, network interruption and logout. Assert no ghost players, duplicate owners or stale reconnect completion.
4. Use the real boot scene and at least one Android IL2CPP build. Capture frame CPU/GPU p50/p95/p99, GC allocation, managed/native memory, snapshot/ack age, interpolation and reconciliation error. Repeat UI lifetimes and AOI spawn bursts.
5. Establish a separate load-generator host where available. Use production-equivalent Protobuf and the selected transport; keep a separate JSON compatibility run. Record exact commits, image IDs, rates, CPU/memory limits, topology and actual successful joins.
6. Test 10/50/100/200 players and higher only after all requested players join. Exercise clustered and dispersed movement, realistic entity counts, idle and combat. Collect gateway ramp failures as well as steady-state metrics; abort capacity conclusions on invalid joins.
7. Inject representative RTT/jitter/loss, short outages and slow dependencies in an isolated test environment. Start with 50/150/300 ms RTT, 1/3/5 percent loss and 5/15/30 second outages; these are proposed test cases, not measured network characteristics.
8. Define the accepted release budget per device and server rate. A 60 Hz critical loop has a 16.67 ms period; a 15 Hz snapshot cadence has a 66.67 ms period. Do not use the snapshot period to pass the critical-loop budget. Require stable queues/memory, no stale-state overwrite, and no reward duplication; choose frame/latency percentile targets with the intended device tier.
